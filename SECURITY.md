# Security and private data

Keep credentials and sensitive campaign content out of public issues. A useful report includes the adapter/client version, the failing operation, a redacted error code and a minimal synthetic reproduction.

Reminders become model context sent through your configured provider. The local database can contain objectives, file paths and evidence summaries. Protect the state directory and backups accordingly.

Conversation binding isolates adapter routes; it is not an OS-user security boundary. Use separate OS users/profiles when stronger separation is needed. Do not widen MCP allowlists or bypass native hook trust to troubleshoot a failure.

## Reporting a vulnerability

Report vulnerabilities privately through GitHub: open the repository's Security tab and select "Report a vulnerability". Don't file a public issue for a suspected vulnerability, and don't post credentials or a working exploit against a real deployment anywhere public.
